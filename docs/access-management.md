# 접속자 관리

관리자 메뉴의 Agent 관리 다음에 접속자 관리를 표시합니다. 일반 사용자에게는 메뉴와 조회 권한을 제공하지 않습니다.

## 수집 기준
- 플랫폼 로그인 성공을 로그인 세션별로 기록합니다. 로그인 실패, 세션 확인, 비밀번호 변경은 로그인 성공 건수로 추가하지 않습니다.
- 정식 플랫폼 게이트웨이를 통한 각 서비스의 /agent 또는 /agent/ GET 응답이 200이고, 유효한 통합 세션이며 초기 비밀번호 변경이 끝난 사용자일 때 첫 진입을 기록합니다.
- 같은 세션·서비스의 기록은 DB UNIQUE 제약으로 한 번만 남습니다. 새로고침과 여러 탭의 동시 접속도 중복되지 않습니다.
- 소개 페이지, API 폴링, 정적 파일 및 실패한 응답은 집계하지 않습니다. 플랫폼 게이트웨이를 우회하는 별도 포트의 직접 접근은 이 수집 범위에 포함되지 않습니다.
- 기존 세션도 배포 후 서비스에 처음 진입하면 기록합니다. 과거 로그인·활동 시각을 접속 이력으로 변환하지 않습니다.
- 로그아웃하거나 계정이 변경되어도 과거 기록은 유지합니다. 접속 당시 이름·사번·팀을 저장합니다. IP, 비밀번호, 원본 세션 쿠키는 저장하지 않습니다. 중복 제거용 세션 해시는 조회 API에 노출하지 않습니다.

## 집계와 조회
GET /api/admin/access?days=7&service=all&page=1
- days: 7 또는 30, 한국 시간 기준 오늘 포함.
- service: all, platform 또는 등록 서비스의 게이트웨이 경로 ID.
- 그래프: 날짜별 COUNT(DISTINCT user_id), 전체 선택 시 서비스 간 동일인 중복 제외. 기록 없는 날짜는 0.
- 요약: 기간 전체의 고유 접속자, 기록 건수, 하루 최다 고유 접속자.
- 목록: 접속 일시 내림차순, 동률은 event_id 내림차순, 페이지당 10개.
- snapshot: 첫 응답의 상한 event_id를 이후 페이지 요청에 전달합니다. 새로고침·기간·서비스 변경 시 해제합니다.
- 첫 진입 이후의 다음 날 활동은 별도 이벤트가 아니므로 이 차트는 DAU/현재 온라인 사용자 지표가 아닙니다.

## 배포 및 검증
먼저 backend/sql/access.sql을 적용한 다음 플랫폼 백엔드를 재시작합니다. 새 platform.access_events 및 access_collection 테이블만 생성하며 기존 사용자·세션 데이터는 변경하지 않습니다.
롤백 시 이전 코드와 정적 진입 파일을 복원하고 기록 테이블은 보존합니다.
모의 세션 단위 테스트, PostgreSQL 연결 전용 임시 테이블을 통한 실제 집계 SQL 검증, 모의 API 브라우저 테스트를 수행했습니다. 실제 사용자를 대신 로그인하거나 테스트 이력을 운영 테이블에 넣지 않았습니다.
